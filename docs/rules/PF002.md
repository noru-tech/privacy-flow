# PF002: Personal data reaches a third-party processor not declared in config

**A flow from personal data to a third-party processor (an analytics, error-tracking, messaging, LLM or other SDK whose vendor the catalogue names, or an HTTP host given as a literal) is a finding unless that processor is declared in `.privacy-flow.yml`.**

| | |
| --- | --- |
| Rule ID | `PF002` |
| Default severity | `high` (error (SARIF)) |
| Fails the default policy (`fail_on: medium`) | yes |
| Fixtures | [`tests/fixtures/ts/pf002-fail`](../../tests/fixtures/ts/pf002-fail) (fails), [`tests/fixtures/ts/pf002-pass`](../../tests/fixtures/ts/pf002-pass) (passes), and the Python equivalents |

## Why it matters

Every processor that receives personal data needs a contract (Art. 28) and an entry in the
record of processing activities (Art. 30). The most common way that record falls out of date is a
code change: a new analytics event with an email address in its properties, a new SDK call, a new
webhook. PF002 turns that change into a finding at review time. Declaring the processor, with a
citation to the DPA or vendor record, turns the same flow into an informational egress fact,
which is how the tool fits a team that already keeps a processor list.

## When it fires

- the sink's class is external (error tracking, analytics, messaging, LLM, outbound HTTP, other
  third-party SDKs), and the call is not a relative URL to the application's own origin, and
- the processor is known: the catalogue sink's `processor`, or the literal host of an outbound
  HTTP call, and
- no `processors` entry in `.privacy-flow.yml` matches it: by `name` (case-insensitive) against the
  catalogue's processor, by `sinks` (catalogue sink ID globs), or by `hosts` (the host or a parent
  domain).

When the processor cannot be named (an HTTP host computed at run time, a model provider chosen
at run time) PF002 does not fire; PF006 and PF003 report those flows. LLM providers are
processors too: an undeclared one gets PF002 and PF003.

## Controls

- GDPR Art. 28 — processor: a vendor receiving personal data on the controller's behalf needs a contract.
- GDPR Art. 30 — records of processing activities: recipients of personal data belong in the record.

These mappings are identifiers with Noru's own short gloss; no normative text from any standard is
quoted. They are a guide for control owners, not a compliance claim, and are pending review by a
privacy lawyer or Noru's compliance lead
([control mapping](../control-mapping.md)).

## Failing example

Fixture: [`tests/fixtures/ts/pf002-fail/`](../../tests/fixtures/ts/pf002-fail/). An email address is sent to PostHog as an event property.

```console
$ piiflow -q scan tests/fixtures/ts/pf002-fail -f json | jq -r '.findings[] | "\(.rule_id) \(.severity) | \(.message)"'
PF002 high | user.contact.email from `user.email` (src/analytics.ts:6) reaches PostHog, a processor not declared in .privacy-flow.yml, at src/analytics.ts:6
```

`piiflow explain <finding ID>` prints the full chain of hops from the source to the sink, with the
source line of each.

## Passing example

Fixture: [`tests/fixtures/ts/pf002-pass/`](../../tests/fixtures/ts/pf002-pass/). The same code with PostHog declared in `.privacy-flow.yml` (`name: PostHog`, citation to the DPA). The flow stays in `flows` and in `egress` with `declared: true`.

## How to fix

- If the vendor is approved: declare it under [`processors`](../configuration.md#processors) with a
  citation to the contract or vendor record. The finding becomes an egress fact.
- If it is not: stop sending the data (send an opaque identifier instead), or route it through an
  approved processor.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in `.privacy-flow/flows.json` (`accepted`, `remediated` or `false_positive`, with
`owner`, `decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`piiflow check .privacy-flow/flows.json --as-of YYYY-MM-DD`. The date is required because the
machine clock is never read. A disposition suppresses the finding from the threshold decision on
that date and leaves the finding, its flow and the summary intact; the next `scan` carries it over
by finding ID, which does not depend on line numbers. Exact rules:
[dispositions](../output.md#dispositions).

```json
{
  "status": "accepted",
  "owner": "privacy@example.com",
  "decided_at": "2026-10-01",
  "expires_at": "2026-12-31",
  "rationale": "Vendor onboarding in progress (VR-0117); declaration follows signature.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `policy.rules.PF002` in [`.privacy-flow.yml`](../configuration.md#policy).
