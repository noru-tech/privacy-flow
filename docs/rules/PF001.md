# PF001: Personal data reaches a log sink

**A flow from personal data to a log sink (console, pino, winston, bunyan, Python `logging`, structlog, loguru, `print`, a logger the analysis recognises by name) is a finding, unless the data is credentials, which PF005 reports instead.**

| | |
| --- | --- |
| Rule ID | `PF001` |
| Default severity | `medium` (warning (SARIF)) |
| Fails the default policy (`fail_on: medium`) | yes |
| Fixtures | [`tests/fixtures/ts/pf001-fail`](../../tests/fixtures/ts/pf001-fail) (fails), [`tests/fixtures/ts/pf001-pass`](../../tests/fixtures/ts/pf001-pass) (passes), and the Python equivalents |

## Why it matters

Logs are copied, shipped, indexed and retained far longer and more widely than the records
they describe, usually by systems with weaker access control than the primary store. Personal data
in a log line is data the organisation did not intend to collect in that place, which is exactly
what data minimisation and security of processing are about. A request body logged in full, an
email address in a debug line, a whole user object passed to `console.log`: most are accidents
that are cheap to fix at review time and expensive to clean up after the fact.

## When it fires

- the sink's class is `log`, and
- the flow's category is not a credential category (`user.authorization.*`, `system.authentication.*`; those are PF005).

Flows whose source is a name the classification table marks as *maybe* personal (`name`,
`payload`, `title`, `value` …) are reported at `info` severity with `needs_review: true`: they
are the review queue, never silently dropped. Request input whose category is `unknown`
(`req.body`, `request.form`) keeps the rule's severity: logging a request body in full is the
case this rule exists for. A flow to a logger matched by its receiver name (an injected
`this.logger`) is marked `heuristic`.

## Controls

- GDPR Art. 5(1)(c) — data minimisation: personal data written to logs is data collected beyond the purpose of the processing that produced it.
- GDPR Art. 32 — security of processing: log stores are rarely protected like the systems of record.
- ISO/IEC 27001:2022 Annex A 8.15 (Logging) — what logs record is in scope of the control; personal data in them is a protection requirement.

These mappings are identifiers with Noru's own short gloss; no normative text from any standard is
quoted. They are a guide for control owners, not a compliance claim, and are pending review by a
privacy lawyer or Noru's compliance lead before the first release
([control mapping](../control-mapping.md)).

## Failing example

Fixture: [`tests/fixtures/ts/pf001-fail/`](../../tests/fixtures/ts/pf001-fail/). `account.email` reaches pino in a template string and `console.log` in a whole object.

```console
$ piiflow -q scan tests/fixtures/ts/pf001-fail -f json | jq -r '.findings[] | "\(.rule_id) \(.severity) | \(.message)"'
PF001 medium | user.contact.email from `account.email (account: Account)` (src/signup.ts:7) reaches a log sink (js.pino) at src/signup.ts:9
PF001 medium | user.contact.email from `account.email (account: Account)` (src/signup.ts:7) reaches a log sink (js.console) at src/signup.ts:10
```

`piiflow explain <finding ID>` prints the full chain of hops from the source to the sink, with the
source line of each.

## Passing example

Fixture: [`tests/fixtures/ts/pf001-pass/`](../../tests/fixtures/ts/pf001-pass/). The same code logs `redact(account.email)`, declared as a sanitiser in `.privacy-flow.yml` with a citation, and the length of the email instead of the email.

## How to fix

- Log identifiers, not values: `{ userId }`, not `{ email }`.
- Pass the value through a redaction helper, and declare it as a sanitiser in
  [`.privacy-flow.yml`](../configuration.md#sanitisers) with a citation to where it was reviewed.
- For request bodies, log the fields you need, not the body.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in `.privacy-flow/flows.json` (`accepted`, `remediated` or `false_positive`, with
`owner`, `decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`piiflow check .privacy-flow/flows.json --as-of YYYY-MM-DD`. The date is required because the
machine clock is never read. A disposition suppresses the finding from the threshold decision on
that date and leaves the finding, its flow and the summary intact; the next `scan` carries it over
by finding ID, which does not depend on line numbers. Exact rules:
[dispositions](../output.md#dispositions).

```json
{
  "status": "accepted",
  "owner": "privacy@example.com",
  "decided_at": "2026-10-01",
  "expires_at": "2026-12-31",
  "rationale": "Debug logging in the signup flow is disabled in production by LOG_LEVEL=info; removal tracked in ENG-412.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `policy.rules.PF001` in [`.privacy-flow.yml`](../configuration.md#policy).
