# PF003: Personal data reaches an LLM provider

**A flow from personal data into a model call (OpenAI, Anthropic, Google Gemini, Mistral, LangChain chat models, the Vercel AI SDK) is a finding, whether or not the provider is declared.**

| | |
| --- | --- |
| Rule ID | `PF003` |
| Default severity | `medium` (warning (SARIF)) |
| Fails the default policy (`fail_on: medium`) | yes |
| Fixtures | [`tests/fixtures/ts/pf003-fail`](../../tests/fixtures/ts/pf003-fail) (fails), [`tests/fixtures/ts/pf003-pass`](../../tests/fixtures/ts/pf003-pass) (passes), and the Python equivalents |

## Why it matters

Sending personal data to a model provider is processing with its own questions: what the
provider retains and for how long, whether it trains on it, where it is processed, and whether the
data is needed for the task at all. Those questions are answered in a DPIA or an AI register, not
in code. PF003 makes each place where personal data enters a prompt, a message list or an
embedding request visible, so that the answer can be recorded once, against a cited flow. It
fires even for a declared provider, because declaring the vendor (PF002) answers a different
question from deciding that this data may go into this prompt.

## When it fires

- the sink's class is `llm`.

The processor is the catalogue sink's vendor; for the Vercel AI SDK, where the model is chosen at
run time, the message says so. Fides egress and the flow facts carry the flow either way, which is
what an AI inventory reads to answer "what data reaches the model".

## Controls

- GDPR Art. 28 and Art. 30 — the model provider is a processor and a recipient.
- ISO/IEC 42001:2023 — AI management: data used by an AI system is in scope of its governance (identifier only).
- EU AI Act Art. 10 — data and data governance for the systems it covers (identifier only).

These mappings are identifiers with Noru's own short gloss; no normative text from any standard is
quoted. They are a guide for control owners, not a compliance claim, and are pending review by a
privacy lawyer or Noru's compliance lead before the first release
([control mapping](../control-mapping.md)).

## How to fix

- Leave personal data out of prompts the task does not need it for; pass an opaque reference and
  resolve it after the model call.
- Where the data is needed, record the decision as a disposition with the DPIA or AI register entry
  as the rationale.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in `.privacy-flow/flows.json` (`accepted`, `remediated` or `false_positive`, with
`owner`, `decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`piiflow check .privacy-flow/flows.json --as-of YYYY-MM-DD`. The date is required because the
machine clock is never read. A disposition suppresses the finding from the threshold decision on
that date and leaves the finding, its flow and the summary intact; the next `scan` carries it over
by finding ID, which does not depend on line numbers. Exact rules:
[dispositions](../output.md#dispositions).

```json
{
  "status": "accepted",
  "owner": "privacy@example.com",
  "decided_at": "2026-10-01",
  "expires_at": "2026-12-31",
  "rationale": "Support drafting needs the customer's name; covered by DPIA-2026-07 and zero-retention terms.",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `policy.rules.PF003` in [`.privacy-flow.yml`](../configuration.md#policy).
