# PF005: Credentials or authentication data reach a log or third party

**A flow of credentials (passwords, password hashes, API keys, access, refresh and session tokens, MFA secrets) to a log or to any external sink is a finding.**

| | |
| --- | --- |
| Rule ID | `PF005` |
| Default severity | `high` (error (SARIF)) |
| Fails the default policy (`fail_on: medium`) | yes |
| Fixtures | [`tests/fixtures/ts/pf005-fail`](../../tests/fixtures/ts/pf005-fail) (fails), [`tests/fixtures/ts/pf005-pass`](../../tests/fixtures/ts/pf005-pass) (passes), and the Python equivalents |

## Why it matters

A credential in a log is a credential available to everyone who can read the log, for as long
as the log is kept. A credential sent to an analytics or error-tracking vendor is a credential
held by that vendor. Both are among the most common causes of account takeover, and both are
easy to introduce: logging a request body that contains a password field is enough.

## When it fires

- the flow's category is a credential category (`user.authorization` and its children,
  `system.authentication` and its children), and
- the sink's class is `log`, or the sink is external, and
- it is not authentication itself: a credential written into request headers (`headers`,
  `Authorization`, `X-API-Key` …) of an outbound HTTP call authenticates to that host and does not
  fire PF005 (or PF006).

Password hashing functions (bcrypt, argon2, scrypt, PBKDF2) are default sanitisers for credentials:
the hash of a password is not the password.

## Controls

- ISO/IEC 27001:2022 Annex A 5.17 (Authentication information) — authentication information is protected through its life cycle.
- ISO/IEC 27001:2022 Annex A 8.15 (Logging) — logs must not become a store of secrets.
- SOC 2 CC6.1 — logical access security over protected information.

These mappings are identifiers with Noru's own short gloss; no normative text from any standard is
quoted. They are a guide for control owners, not a compliance claim, and are pending review by a
privacy lawyer or Noru's compliance lead
([control mapping](../control-mapping.md)).

## Failing example

Fixture: [`tests/fixtures/ts/pf005-fail/`](../../tests/fixtures/ts/pf005-fail/). The login handler logs the username and the password from the request body.

```console
$ piiflow -q scan tests/fixtures/ts/pf005-fail -f json | jq -r '.findings[] | "\(.rule_id) \(.severity) | \(.message)"'
PF001 medium | user.account.username from `username` (src/auth.ts:8) reaches a log sink (js.winston) at src/auth.ts:9
PF005 high | credentials: user.authorization.password from `password` (src/auth.ts:8) reach a log sink at src/auth.ts:9
```

`piiflow explain <finding ID>` prints the full chain of hops from the source to the sink, with the
source line of each.

## Passing example

Fixture: [`tests/fixtures/ts/pf005-pass/`](../../tests/fixtures/ts/pf005-pass/). The handler hashes the password with bcrypt and logs only the hash's length.

## How to fix

- Remove the credential from the log line or the payload. There is rarely a reason to keep it.
- Rotate the credential if the code has run in an environment whose logs are retained.

## Recording a disposition

A finding is never deleted. To record a human decision about it, edit only the finding's
`disposition` in `.privacy-flow/flows.json` (`accepted`, `remediated` or `false_positive`, with
`owner`, `decided_at`, `rationale`, and `remediated_at` or an optional `expires_at`), then run
`piiflow check .privacy-flow/flows.json --as-of YYYY-MM-DD`. The date is required because the
machine clock is never read. A disposition suppresses the finding from the threshold decision on
that date and leaves the finding, its flow and the summary intact; the next `scan` carries it over
by finding ID, which does not depend on line numbers. Exact rules:
[dispositions](../output.md#dispositions).

```json
{
  "status": "accepted",
  "owner": "privacy@example.com",
  "decided_at": "2026-10-01",
  "expires_at": "2026-12-31",
  "rationale": "False positive: `token` here is a CSRF nonce, not an authentication credential (see SEC-77).",
  "remediated_at": null
}
```

To change how the rule is enforced rather than record a one-off decision, set its severity or
disable it under `policy.rules.PF005` in [`.privacy-flow.yml`](../configuration.md#policy).
