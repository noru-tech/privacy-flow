# Fides egress declarations

For a full data map of a repository (its systems, datasets, the flows between them and proposed
privacy declarations, merged into the file you keep), use [`piiflow datamap`](datamap.md). This
page is about the egress fragment of a single system that `scan` writes.

`piiflow scan --format fides` (or `-o egress.yml`) writes the flows that leave the system as
**egress declarations** of a Fides `system`, to merge into a Fides data map such as the
`.fides/datamap.yml` privacy-datamap maintains. privacy-datamap maps what a repository stores;
this fills in where it sends it.

```yaml
# Fides egress declarations generated by privacy-flow 0.1.0 from 3f1c…
# A fragment to merge into a Fides data map (for example .fides/datamap.yml): it carries
# egress only. Privacy declarations (data use, data subjects, legal basis) are judgements
# this tool does not make; add them where you maintain the system.
system:
  - fides_key: "checkout_service"
    name: "Checkout service"
    # Keys starting with unresolved_ are destinations the code does not name (a host
    # computed at run time, a provider chosen by configuration). Replace each with the
    # receiving system's key, or declare the processor in .privacy-flow.yml and scan again.
    egress:
      # Mixpanel via analytics
      - fides_key: "mixpanel"
        type: "system"
        data_categories:
          - "user.demographic.religious_belief"
      # Unresolved http destination, sent from src/services/ordering.ts:17
      - fides_key: "unresolved_http_ordering"
        type: "system"
        data_categories:
          - "user.financial.credit_card"
```

## Field names

The field names follow the Fideslang version the vendored taxonomy snapshot comes from (3.1.3,
see [`vendor/SOURCE.md`](../vendor/SOURCE.md)). In that version `System.egress` is a list of
`DataFlow` objects with `fides_key` (the receiving system), `type` (`system`, `dataset` or
`user`; always `system` here) and an optional `data_categories` list of category keys. This was
checked against `src/fideslang/models.py` at tag 3.1.3.

## What is written

- One `DataFlow` per processor, across sink classes, for flows to an external sink (error
  tracking, analytics, messaging, LLM, outbound HTTP with a literal host, other third-party SDKs).
  Logs, browser storage and relative URLs are not egress.
- The `fides_key` is the processor's `fides_key` from `.privacy-flow.yml` when declared, otherwise
  a slug of its name: the declared name (`Acme CRM` → `acme_crm`), else the catalogue's
  (`PostHog` → `posthog`), else the literal host (`api.example.com`). A declaration names the
  processor however it matched: by name, by sink ID or by host.
- `data_categories` lists only keys of the vendored taxonomy. Request input of category `unknown`
  has no Fides key; a comment says the flow also carries data of unknown category, to review.
- A comment above each entry names the processor, the sink classes, and whether it is declared.
- Egress to a destination the code does not name (a host computed at run time, a model provider
  chosen by configuration) is still a `DataFlow`, so a first scan with no configuration shows
  where data goes. Its key is a placeholder, `unresolved_<sink class>_<file>`, one per sink class
  and sending file (`unresolved_http_ordering_service`; directories are added when two files
  share a name), with a comment naming the call sites. Replace it with the receiving system's
  key, or declare the processor under `processors:` (by `sinks` or `hosts`) and scan again. Like
  `this_system`, a placeholder names no system in your data map; the Fides CLI expects every
  receiving system to exist there (see below).
- `system.fides_key` and `name` come from `system:` in `.privacy-flow.yml`; without it the key is
  `this_system` and a comment says to set it.

## What is not written

The fragment carries no `privacy_declarations`, `system_type` or dataset references. Data uses,
data subjects and legal bases are judgements, not flow facts; they stay with whoever maintains
the data map (a human, or Noru), as the [open/closed line](../NOTES.md) puts it. The receiving
systems are referenced by key; the Fides CLI expects them to exist in the data map you merge into.

## Merging

The fragment is YAML with one `system` entry. Merge its `egress` list into the matching system of
your data map by hand or with your own tooling; `piiflow` never edits a data map. Re-running the
scan regenerates the fragment from scratch, so review the diff.
